پروژه ۱۶ — از لیست هاردکد تا یک RAG واقعی

در پروژه ۱۵ داکیومنت‌ها چهار تا رشته داخل کد بودند و وکتورها داخل یک لیست پایتون. این کار می‌کرد، ولی به هیچ‌کدام از مشکلات دنیای واقعی برخورد نکردی. این پروژه دقیقاً همان مشکلات را اضافه می‌کند: فایل واقعی، chunking، و vector store.

۱. مشکل اول: فایل‌ها بزرگ‌اند

فرض کن یک فایل ۲۰ صفحه‌ای داری. اگر کل فایل را یک وکتور کنی، سه چیز خراب می‌شود:

  • معنی رقیق می‌شود. یک وکتور ۳۸۴ بعدی نمی‌تواند ۲۰ صفحه موضوع مختلف را همزمان نمایندگی کند. میانگین همه‌چیز می‌شود، یعنی هیچ‌چیز.
  • context window پر می‌شود. برای جواب دادن به یک سوال کوچک، ۲۰ صفحه را به مدل می‌فرستی. هم گران است هم دقت پایین می‌آید.
  • نمی‌توانی cite کنی. می‌گویی «جواب توی این فایل بود» — ولی کجای فایل؟

راه‌حل: فایل را به تکه‌های کوچک‌تر بشکن. به هر تکه می‌گوییم chunk.

اندازه chunk یک trade-off است

حالتچه اتفاقی می‌افتد
chunk خیلی کوچک (مثلاً ۵۰ کاراکتر)context کافی ندارد. «این کار ممنوع است» بدون اینکه معلوم باشد «این» چیست. retrieval هم پر از نویز می‌شود.
chunk خیلی بزرگ (مثلاً ۵۰۰۰ کاراکتر)همان مشکل کل‌فایل، فقط کوچک‌تر. یک chunk چند موضوع دارد و وکتورش بی‌دقت می‌شود.
معمول در عملحدود ۳۰۰ تا ۱۰۰۰ کاراکتر. باید تست کنی، فرمول ندارد.

چرا overlap لازم است؟

اگر دقیقاً سر ۵۰۰ کاراکتر ببری، ممکن است وسط یک جمله یا وسط یک ایده بشکنی. جمله‌ی «دلیلش این است که rollback مایگریشن را برنمی‌گرداند» ممکن است نصفش در chunk اول و نصفش در chunk دوم بیفتد — و آن‌وقت هیچ‌کدام جواب کامل نیستند.

overlap یعنی هر chunk چند کاراکتر آخر chunk قبلی را هم تکرار می‌کند. مثل یک بالشتک. معمولاً ۱۰٪ تا ۲۰٪ اندازه‌ی chunk.

CHUNKING WITH OVERLAP (chunk_size = 500, overlap = 100)
chars 0 → 500
chars 400 → 900
chars 800 → 1300
next_start = start + chunk_size - overlap
تله: اگر overlap >= chunk_size باشد، next_start جلو نمی‌رود و حلقه‌ات بی‌نهایت می‌شود. این را در کدت هندل کن.

۲. مشکل دوم: وکتورها باید جایی بمانند

در پروژه ۱۵ هر بار که برنامه را اجرا می‌کردی، همه‌ی داکیومنت‌ها دوباره embed می‌شدند. با ۴ داکیومنت اهمیتی ندارد. با ۱۰٬۰۰۰ فایل، هر اجرا چند دقیقه طول می‌کشد و (اگر API باشد) پول می‌دهی.

۳. vector store دقیقاً چیست؟

یک دیتابیس که به‌جای «کجا فیلد X برابر Y است»، جواب می‌دهد به «کدام وکتورها به این وکتور نزدیک‌ترند».

تو در پروژه ۱۵ این را دستی نوشتی: similarity را با همه‌ی داکیومنت‌ها حساب کردی، sort کردی، top_k را برداشتی. این روش اسمش brute force است و برای ۴ داکیومنت عالی است. برای یک میلیون وکتور کند است.

vector store دو کار برایت می‌کند:

  • index — ساختار داده‌ای مثل HNSW که به‌جای چک کردن همه، فقط بخش کوچکی از فضا را می‌گردد. جواب تقریبی است (ANN = Approximate Nearest Neighbor) ولی خیلی سریع‌تر.
  • persistence + metadata — وکتور، متن اصلی، و متادیتا (source، chunk_index، تاریخ...) کنار هم ذخیره می‌شوند و بعد از restart سر جایشان هستند.

۴. Chroma در عمل

import chromadb

# a client that writes to a folder on disk
client = chromadb.PersistentClient(path="chroma_db")

# a collection = one logical set of chunks
collection = client.get_or_create_collection(
    name="handbook",
    configuration={"hnsw": {"space": "cosine"}},
)

# write: ids / embeddings / documents / metadatas are parallel lists
collection.add(
    ids=["deployment.md#0"],
    embeddings=[[0.12, 0.03, ...]],
    documents=["Deployments to production are allowed..."],
    metadatas=[{"source": "deployment.md", "chunk_index": 0}],
)

# read: nearest neighbours of a query vector
res = collection.query(query_embeddings=[q_vec], n_results=4)
مهم: نتیجه‌ی query یک dict از list of lists است، چون می‌توانی چند سوال را باهم بپرسی. تو یک سوال پرسیدی، پس همه‌چیز در ایندکس [0] است: res["documents"][0]
distance ≠ similarity. Chroma با فضای cosine مقدار فاصله برمی‌گرداند: کوچک‌تر = بهتر. در پروژه ۱۵ برعکس بود (بزرگ‌تر = بهتر). رابطه: similarity = 1 - distance. اگر این را جابه‌جا بگیری، فیلترت دقیقاً برعکس عمل می‌کند.

چرا cosine و نه پیش‌فرض؟

پیش‌فرض Chroma فاصله‌ی L2 (اقلیدسی) است. مدل‌های embedding مثل all-MiniLM برای مقایسه‌ی cosine آموزش دیده‌اند — یعنی جهت وکتور معنی دارد، نه طولش. باید فضا را به cosine ست کنی تا با مدل هماهنگ باشد.

۵. سوال id ها

هر chunk باید یک id یکتا داشته باشد. این انتخاب مستقیماً تعیین می‌کند اجرای دوم ingest.py چه می‌کند:

روشاجرای دوم
id تصادفی (uuid)همه‌چیز دوباره اضافه می‌شود → داده دوبرابر، retrieval پر از تکرار
id پایدار مثل "deployment.md#3" + upsertهمان chunk جایگزین می‌شود → تمیز، ولی chunk های حذف‌شده باقی می‌مانند
delete collection سپس rebuildهمیشه درست، ساده، ولی همه‌چیز دوباره embed می‌شود

در این پروژه هر کدام را می‌خواهی انتخاب کن — ولی در کامنت بنویس چرا.
