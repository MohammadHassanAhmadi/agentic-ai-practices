۴. محدودیت شناخته‌شده — تست ۸

سوال: How much vacation do I get after a production incident?

پاسخ سیستم: I don't know based on the provided documents.

سند می‌گوید «additional time off in lieu if they are paged outside working hours». سوال می‌گوید «vacation» و «production incident». هیچ کلمه‌ی مشترکی ندارند و بردارهایشان به‌اندازه‌ی کافی نزدیک نیستند — حتی با TOP_K = 6 آن chunk بازیابی نشد.

این یک باگ نیست — محدودیت ذاتی dense vector search است. هیچ‌کدام از ابزارهای این پروژه (اندازه‌ی chunk، مرز chunk، prompt، top_k) حلش نمی‌کنند.
راه‌حل واقعیچه می‌کند
hybrid search (BM25 + vector)جستجوی کلیدواژه‌ای در کنار معنایی — «incident» را لغت‌به‌لغت پیدا می‌کند
reranker (cross-encoder)سوال و chunk را با هم می‌خواند، نه جدا — ربط را خیلی دقیق‌تر می‌سنجد

۶. ارتباط با کار واقعی

این دقیقاً شکل هر سیستم RAG در production است: یک indexing job آفلاین و یک query path آنلاین که فقط از طریق vector store با هم حرف می‌زنند.

در production چه فرقی دارد

  • re-index افزایشی است (بر اساس content hash) — نه rebuild کامل
  • store یک سرویس مدیریت‌شده است: pgvector، Pinecone، Azure AI Search
  • chunking ساختارآگاه است: تیترها، جدول‌ها، بلوک‌های کد جداگانه هندل می‌شوند
  • بین retrieval و LLM یک reranker هست
  • نام مدل embedding کنار داده ذخیره می‌شود — عوض شدنش یعنی rebuild اجباری

۷. سوال و جواب مصاحبه

جواب‌ها انگلیسی‌اند چون در مصاحبه همین‌طور می‌گویی‌شان. هر کدام به یک چیز واقعی در همین پروژه وصل است — همان چیزی که جواب را باورپذیر می‌کند.

Q1 · How do you pick chunk size? What is the trade-off?

There is no formula — you measure. Too small and each chunk loses the context that makes it meaningful: in my project, 300-character chunks separated a markdown heading from the paragraph under it, and retrieval got measurably worse. Too large and one vector has to represent several topics at once, so it matches everything weakly and nothing strongly. I settled on 500 characters with 100 overlap, but the bigger decision was where I cut, not how much. One hard ceiling: the embedding model's token limit — all-MiniLM-L6-v2 caps at 256 tokens and silently truncates past it, so I assert on token count before embedding instead of trusting the character count.

Q2 · Why does chunk overlap exist?

A hard cut can land in the middle of a sentence or an idea, so the fact you need ends up split across two chunks and neither one answers the question. Overlap repeats the tail of the previous chunk at the start of the next one, so a fact near a boundary survives in at least one complete chunk. Typically 10–20% of chunk size. The implementation trap is that if overlap is greater than or equal to chunk size, the loop never advances and hangs — so I validate that up front.

Q3 · How do you re-index when a document changes?

The unit of update is the file, so I store source and a content hash in each chunk's metadata. On ingest I hash the file and compare: unchanged means skip, changed means delete that file's chunks and re-add only them, and a file that no longer exists on disk gets its chunks deleted. Full rebuild is fine at small scale — I used it here because it can never leave stale data behind — but it does not scale. The dangerous middle ground is append-only: it raises no error, it just quietly leaves the old version of a document sitting next to the new one, and the model can answer from either.

Q4 · When does vector search fail?

When the question and the document mean the same thing but share no vocabulary. I hit this concretely: my document said "additional time off in lieu if they are paged outside working hours", and the question asked "how much vacation do I get after a production incident". Semantically the same, but the right chunk did not come back even in the top 6. Embeddings capture similarity, not reasoning — nothing about chunking, chunk size, prompt wording or top_k fixes it. The real fixes are hybrid search (BM25 alongside vector), a cross-encoder reranker, or LLM query rewriting.

Q5 · How do you stop the model hallucinating citations?

Two layers. First the prompt: every context line is prefixed with its source, and the model is told to return only the sources it actually used — not everything it was shown. Second, code: the answer comes back as a structured object with a used_sources list, and I check every entry against the set of chunks actually retrieved for that question. Anything not in that set is a hallucination and gets flagged. The prompt reduces the problem; only the code check catches it.

Q6 · Why cosine distance and not the default?

Chroma defaults to L2 (Euclidean) distance, but embedding models like all-MiniLM are trained for cosine similarity — direction carries the meaning, magnitude does not. Mismatching them degrades ranking silently. Also worth knowing: Chroma returns distance, where smaller is better, while a hand-rolled cosine similarity returns the opposite. In my project the correct answers scored 0.33–0.58 distance and a completely off-topic question scored 0.92, so the real relevance boundary sat near 0.8, not the 0.5 you would guess. An intuitive threshold would have thrown away most of the correct answers.

Q7 · Why split indexing and querying into two processes?

Cost and latency. Embedding is the expensive step and the documents do not change per question, so you pay for it once offline and reuse it for every query. The vector store is the only thing the two halves share. It also means the two sides can scale and be deployed independently — the indexing job can be a nightly batch while the query path stays a low-latency service. The constraint is that both sides must use the same embedding model: different models put vectors in different spaces, and comparing across them is meaningless.

Q8 · How would you improve retrieval quality from here?

In order of payoff. First hybrid search — run BM25 keyword search alongside vector search and merge the results, which catches exact terms that embeddings miss. Then a cross-encoder reranker: retrieve a wider set, say top 20, and rescore it with a model that reads the question and the chunk together rather than embedding them separately. Then query rewriting, where an LLM expands the user's wording into the vocabulary the documents actually use. Structure-aware chunking that keeps headings attached to their sections also helps, and I saw that effect directly in this project.
